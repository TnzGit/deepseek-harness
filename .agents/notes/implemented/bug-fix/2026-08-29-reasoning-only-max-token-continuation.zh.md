# Agent Note: 纯推理响应达到输出上限时自动续跑一次

Status: implemented

[English](2026-08-29-reasoning-only-max-token-continuation.md) | 中文

## Problem

长思考模型可能把单次请求的全部输出预算消耗在私有推理中，以 `max-tokens` 结束，却没有可见回答或工具调用。此时推理仍在推进、任务也尚未完成，但轮次看起来已经停住。统一提高所有模型的输出上限只能推迟相同的终止条件，还会减少长会话可用的输入余量。

## Decision

agent loop 只识别一种狭窄且可恢复的形态：成功的 `max-tokens` 结束，包含非空推理，没有非空可见文本，也没有工具调用。循环会提交该 assistant 消息，追加持久化的 `agent/max-token-continuation` 事件，并在同一轮次中打开新步骤。请求重建会把该事件转换为一条内部用户消息，要求模型沿用已提交的推理，并产出最终回答或下一个必要工具调用。

`maxTokenContinuations` 按轮次限制该行为，默认一次，位于实时 `agent-loop` Settings 段中，也接受零来禁用恢复。该值在轮次边界捕获。如果恢复请求在预算耗尽后再次遇到同样情况，轮次会以 `{ kind: 'max-tokens', autoContinuation: 'exhausted' }` 结束；客户端随后会说明自动续跑已经执行过。这个上限能避免反复把预算耗尽在推理中的模型无限运行。

续跑是普通的下一步骤请求。它不会覆盖提供方、模型、输出上限、thinking 或 reasoning effort。尤其是，恢复会保留原路由的 thinking 设置，而不是降低或关闭它。包含可见部分文本或工具调用的响应仍会在达到上限时结束，因为重放它们可能导致可见输出或副作用重复。

## Alternatives considered

**把模型 `maxTokens` 提高到 65,536。** 不作为永久机制。它可以是部署选择，但模型仍可能耗尽更大的上限，而且预留该预算会减少上下文压力判断所使用的输入预算。

**恢复时关闭或降低 thinking。** 不采用，因为这会在任务最困难的节点悄然改变用户选择的模型行为。续跑会保留实际生效的请求设置。

**不限制续跑次数。** 不采用，因为反复出现的纯推理结束可能无限消耗时间和算力。

**自动续跑可见部分回答或工具调用。** 不采用，因为下次请求可能重复文本或再次发出操作。这些情况保留现有的显式“继续”流程。

## Verification

agent-loop 测试覆盖一次续跑成功、两次请求的 reasoning effort 一致、有界耗尽、通过 Settings 禁用，以及存在可见输出时不触发。真实 Cordis Loader 快照通过 DeepSeek 直连 SSE 适配器制造纯推理 length 结束，并在请求线上确认两次调用都保留 `thinking: { type: 'enabled' }`、`reasoning_effort: 'max'` 和相同输出上限。客户端投影与渲染测试覆盖普通提示和自动续跑耗尽提示。

## Consequences

在常见的只需额外一次请求的情况下，纯推理输出上限结束无需用户输入即可恢复。若模型继续思考，额外请求会按设计再消耗一份完整输出预算。持久事件重建让回放、持久化恢复和请求不变量对恢复提示保持一致。运维人员可以设置 `maxTokenContinuations: 0` 保留旧的终止行为，也可以选择更大的上限并接受相应算力成本。
